## CR-04 · Manifest contract

Direction: data→app. Mirror at baseline:
> New families are additive and need no app change (the app already keys by path). Renaming or removing `recordCount` / `schemaVersion` / `lastModified` / `inProgress` is breaking and needs both repos. **Renaming the top-level `files` map, or the per-entry `lastModified`, breaks a second app-side reader that `getManifestEntry` does not shield** — `ktcHistory.js` enumerates `Object.keys(manifest.files)` to discover KTC snapshots and compares `lastModified` for cache invalidation (CR-17); it degrades to an empty history with no error. Note the `inProgress` convention split: nflverse families register `inProgress: false` even while the current season mutates; KTC's `inProgress: true` is a legacy current-value marker, not a pattern to propagate (CR-17). **A second `allowInProgress: true` opt-in exists since in-season-app-read.md — `loadCurrentSeasonTotals` (CR-02) — and it is NOT the same situation as KTC's.** KTC's `inProgress: true` is a mislabel: a KTC snapshot is a completed, immutable capture registered with a "current value" flag that is wrong about the file. An in-progress season-totals file genuinely *is* incomplete and genuinely *should* be read while incomplete — that is the entire point of reading it. The convention this Mirror warns against is using `inProgress` to mean "latest"; season-totals uses it to mean "not finished," which is its actual, documented meaning. Do not read this Mirror's "not a pattern to propagate" line as blocking a genuinely-incomplete family from opting in the same way — read it as blocking a *mislabeled* one. A third `allowInProgress: true` opt-in exists since advstats-live-season-column.md — `loadAdvStatsForSeason` (CR-07), the live-season exact-year advstats read; same genuinely-incomplete case as season-totals, so a future `inProgress: true` on the live advstats file would still render.

Fires because `scripts/migrate-weekly-stats.mjs` writes `manifest.json` through `updateManifestEntry` (`recordCount` unchanged, `schemaVersion: 4`, `inProgress: false`). No field is renamed or removed. B3 adds the script to CR-04's Data side and Triggers.

## CR-29 · Manifest transport (raw GitHub primary, jsDelivr fallback) *(new — manifest-raw-source.md, 2026-10-13)*

Direction: both. Mirror at baseline:
> Renaming or transferring the repository, renaming `main`, making it private, or moving `manifest.json` off the repository root breaks the raw candidate and the app silently falls back to the jsDelivr manifest, which is no longer purged and can be hours stale — **nothing app-side goes red**; update `VITE_DATA_STORE_URL` and `rawManifestUrl` in the same cycle. Changing the base URL to a form `rawManifestUrl` does not match turns the raw candidate off with no error (the capture build in `daily-snapshot.yml:75` deliberately uses a `raw.githubusercontent.com` base, which does not match, so it reads the manifest exactly as before). A workflow that adds a purge of `manifest.json` re-creates the throttling red this entry removed; a workflow that commits a new family path without purging it exposes a possible cached 404. The raw copy lags a push by up to 5 minutes (`max-age=300`), the jsDelivr family file lags by at most the job's verify loop: a manifest that is briefly *older* than the files is harmless (older `lastModified`, newer bytes), a manifest *newer* than a stale family file is not (the app would cache stale bytes under the new `lastModified`) — which is why the job's family verify must finish before the job succeeds, and why the app refuses to cache a body that disagrees with its entry. Changing what a family's `recordCount` counts, or writing `generatedAt` more than 60 s before the manifest stamp, makes every load of that family look stale: nothing goes red, the app just stops caching it and re-fetches each session — update `expectedRecordCount` in the same cycle.

Fires: the migration is a new writer computing `recordCount` relative to `updateManifestEntry` (unchanged count). Because the count is unchanged, the R4 body-vs-entry check **cannot** catch a stale pre-migration body served under the new `lastModified`, and completed seasons never move `lastModified` again. So Stage C must run `bin/purge-cdn.mjs` on all 14 paths straight after the push, and the verify must pass before sign-off (§6). `generatedAt` is not written into season files.
